# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Par Arrows is a 3D arrow-removal puzzle game (desktop and mobile web). Rotate a cube and tap an unobstructed arrow to send it off the surface. A green stop circle parks a passing head until it is tapped again. Two or three arrows with overlapping tails form a group that moves together. A first collision costs one life and marks the arrow or entire group red. A cyan chevron spot bends a passing head onto its heading, and a cube carrying chevron spots needs that turn to clear. A magenta flip spot works the same way but reverses its direction each time an arrow has fully passed it, and an amber rotor spot turns its direction a quarter clockwise each time instead. Paired wormhole rings teleport a moving head onto the partner cell in the same step, keeping its face-local heading, so a lane blocked on one face can run clear on another; a blocked exit past a portal is an ordinary collision that rewinds the arrow back through it. A cracked fragile cell survives one crossing, then collapses into a hole, and a head that later runs into the hole falls into the cube and is removed at the cost of one life. A barred gate blocks its lane until any arrow's head crosses its key elsewhere on the cube, which opens it for good; running into a closed gate rewinds the arrow at no cost, because a gate is terrain, not a collision. A silver mirror reflects a passing head across its diagonal, so the same mirror sends a northbound arrow east and a southbound arrow west — two arrows, one mirror, two destinations. An amber leap pad skips the next cell: a head entering it lands two cells on and nothing on the skipped cell ever triggers, so a lane blocked by exactly one occupied cell runs clear. Arrows never collide with themselves: a head sent back the way it came travels over its own body. TypeScript, three.js, Vite, and the Bun toolchain, with no UI framework.

## Commands

Bun is the package manager and test runner — not npm/node.

```sh
bun install --frozen-lockfile   # install
make dev                        # Vite dev server at http://localhost:8057 (strict port)
make dev-stop                   # release the dev port
make checkall                   # full gate: format-check, lint, typecheck, test, build, icons-check
make test                       # bun test (unit tests in tests/*.test.ts)
bun test tests/core.test.ts     # one test file
bun test -t "wrapping"          # tests matching a name
make fmt                        # biome format --write (format only files you touched)
make icons                      # regenerate icon suite from SVG sources (make icons-check verifies)
```

Browser (Playwright) tests are separate from unit tests and build/serve production assets on port 8058 with a headed browser:

```sh
make browser-install            # playwright install chromium
make browser-test               # builds, serves, runs tests/browser-runner.ts
BROWSER_ENGINE=webkit make browser-test   # after: bunx playwright install webkit
```

GitHub Actions runs `make checkall` on every push. Run the browser suite locally on a machine with a real headed browser and working WebGL; a virtual X display does not provide valid canvas-pixel evidence.

`make pre-commit` runs the pinned secret-scanning and project checks over all files.

## Architecture

The layering is the central design constraint:

- **`src/core` — pure game logic.** Topology (face/cell grid, seams, `stepSurface`), movement (`simulateMove`/`applyMove` returning a fully deterministic `MoveResult` with route, waypoints, contact/exit traces), game state, and validation (`solveLevel` — every authored and generated level is solver-validated). No DOM, no rendering, no storage imports. Core is renderer-neutral: it produces positions/traces the renderer animates.
- **`src/content` — level content.** Authored levels (`intro.ts`: level 1 and the authored level-11 wrap-intro cube, with level 5 in `stop-intro.ts`, level 15 in `overlap-intro.ts`, level 20 in `directional-intro.ts`, level 25 in `double-intro.ts`, level 30 in `flip-intro.ts`, level 35 in `wormhole-intro.ts`, level 40 in `rotor-intro.ts`, level 45 in `fragile-intro.ts`, and level 50 in `lock-intro.ts`, and level 55 in `mirror-intro.ts`, and level 60 in `leap-intro.ts`) plus the deterministic seeded generator (`procedural.ts`). Generation runs in a Web Worker (`generation-worker.ts`) driven by `level-loader.ts`; results are validated before play. `level-preview.ts` implements the URL selectors (`?level=N`, `?feature=wrap|overlap|stop|directional|double|flip|wormhole|rotor|fragile|lock|mirror|leap`, `?wraps=N`) — preview sessions must never write or clear campaign saves.
- **`src/render/renderer.ts`** — three.js scene, arrow ribbon geometry, camera rotation, animation. It animates the core's outcome; it never decides life deductions or move legality.
- **`src/app.ts` (`ParArrowsApp`)** — orchestrator: mode (demo/campaign), lives, hints, celebration/confetti, HUD, and wiring input → core → renderer → storage; while a scripted walkthrough expects an arrow, only that arrow (or its group) responds to taps until the script's interactions finish. `src/input.ts` handles pointer/touch/gesture disambiguation (tap vs drag vs pinch). `src/storage.ts` is the only module touching `localStorage`. The settings panel's mechanics guide (`src/help.ts`) lists each mechanic whose intro cube the save has reached (`campaignUnlockedLevelId`), each with a canvas thumbnail from `public/help/` recaptured by `scripts/capture-help-shots.ts`; tapping an entry opens it enlarged in a dialog, and unreached mechanics stay hidden. `src/pwa.ts` classifies the browser (`detectInstallContext`, pure and unit-tested; an iPadOS desktop user agent with touch counts as iOS) and holds per-browser `installSteps`; `app.ts` opens the install `<dialog>` on first launch in a mobile browser tab that is not running standalone, records `installPromptDismissed` in settings when it closes, and reopens it from Settings → How to install. `?test=1` and preview sessions never auto-open it unless `pwaPrompt=1` forces it, because a modal dialog would make the page inert for every other browser suite; `render_game_to_text` reports `pwaPrompt` (`open`, `browser`, `mobile`).

### Domain model (`src/core/types.ts`)

A level is a cube of `FaceId` faces, each an integer cell grid. Arrows are ordered `Cell` paths with a head (active) and tail. Moves resolve to `exit` (the arrow or whole group leaves), `paused` (the head parked on a stop circle), `blocked` (first collision costs one life and turns the arrow or whole group red, with repeated failures free), `gated` (the head met a closed gate; a free rewind), `fall` (the head entered a collapsed fragile cell; the arrow or whole group is removed for one life), or `invalid` (a continuation loop or a topology fault, never a life). Occupancy comes from other arrows only, so an arrow never collides with its own body. `EdgePolicyDefinition` declares boundary rules. Its `policy: "continue"` is a wrapping (yellow) edge where a moving head wraps to a neighbor face instead of exiting.

### Stop circles

**Gameplay rules:** `LevelDefinition.stops` lists cells that carry a green circle. A head that steps onto one parks there and the arrow keeps its new cells; the attempt costs nothing and removes nothing. Tapping it again continues forward, and the cell it is leaving never re-parks it. Parking is the way to push an arrow forward to unblock others without it colliding. A collision after leaving a circle costs the usual single life, turns the arrow red, and rebounds it to the circle rather than to its authored start. A circle may not sit on any arrow's starting cell or share a cell with a spot, and validation rejects a circle that would park an arrow folded back over its own body (see Flip spots). A group with a shared tail parks as one unit at the earliest member's circle, every member travelling the same distance; a collision on the same step as a circle still costs the life.

**Introduction:** Level 5 is a level-1-style 4 x 4 cube with three arrows, five lives and no yellow edges. Its three front-face arrows form a cycle — the parker blocks the freed arrow, the freed arrow blocks the blocker, and the blocker sits in the parker's lane past the circle — so parking is the only opening move. `tests/stop-content.test.ts` pins this by asserting the same cube with `stops: []` is unsolvable. Levels 1-4 carry no circles; generated levels from 6 onward carry 0-3 circles, and level 6 always carries one. Every generated level that carries at least one circle embeds a parking-required deadlock from the core catalog, so parking is required to clear it; zero-circle levels clear without parking. `?feature=stop` opens the introduction without changing campaign saves.

**Implementation:** `src/core/stops.ts` derives each arrow's static track (authored path plus its pure-topology head route) and its current path at a given offset, so `GameState.offsets` is the single source of where every single arrow and group sits on levels without flip spots. On a level with any flip spot, a lone single arrow's route depends on spot state, so it parks by storing its exact cells in `settledPaths`, as parked doubles do. `simulateMove` builds occupancy from current paths and returns `paused` with `pausedSteps`; `applyMove` advances the whole group's offsets without touching lives. Generated circle levels require parking by construction: the generator embeds a parking-required deadlock core drawn from a seeded catalog (`PARK_PATTERNS`, eight patterns — the level-5 classic, a long-lane stretch, a four-arrow cascade, and a two-circle double park, plus twist (an L-shaped freed lane), crossfire (four arrows, a parker plus three followers, with an interleaved unwind), twin (two independent one-circle deadlocks that each need their own parker), and bounce (the parker starts head-on into its own static spot and reaches its circle only by reversing back over its own body; its spot spends the cube's static-spot plan, so it is drawn only on a spot-plan pass onto a planned face); every generated id draws from the whole catalog, limited only by its stop budget) from a dedicated `:park-core` seeded stream, and the core geometry proves the requirement — with the circles stripped, every core arrow's first route cell hits another core arrow, and `others` lists each pattern's arrows in reverse unwinding order so the certificate unwinds them after the park. `validateGenerated` in `procedural.ts` replays a park-prefixed certificate cheaply, `parkingCore` replays the core-only certificate at placement time so a wrap config that would strand a core arrow rejects the placement instead of failing the level, and reserving the core's circle cells keeps the level replay infallible without restarting construction. `solveLevel` clears greedily and only backtracks over parking choices, which is what authored cubes like level 5 need. Do not put the backtracking search on the generation path.

### Overlapping tails

**Gameplay rules:** Two or three single-ended arrows may share a continuous tail segment in the same direction. Arrowheads must remain separate. A point crossing does not create a group. Tapping any exposed portion of any member, including its head, individual body or shared tail, activates every connected member at once. Members never block each other or cross each other's travel paths.

If any member hits an outside arrow, every member reverses together at the earliest contact, returns to its exact starting path and stays red, including members whose own exits were clear. The first failure costs one life for the whole group; repeated failures are free. A successful attempt removes every member together. Only one arrow or group attempt runs at a time, while orbit and zoom remain available. Press selection and safe hints highlight the entire group.

**Introduction:** Level 15 uses a level-1-style 4 × 4 cube with six arrows, five lives and no yellow wrapping edges. A pair and its removable blocker occupy the front face; a trio occupies the left face. Generated levels before 16 carry no groups; generated levels from 16 onward include pairs/trios, including cubes that carry spots. `?feature=overlap` opens the introduction without changing campaign saves.

**Implementation:** `src/core/overlap.ts` derives connected groups from shared directed non-head links, including staggered tails. Validation rejects groups larger than three, shared heads, point crossings, opposite-direction overlap, double-ended members and intersecting future member routes, even when an outside blocker initially hides the problem. A group may share a cube with static or flip spots, but validation rejects a group any of whose members' tracks (body included) enters a spot cell, because a group moves on one shared offset along static tracks. Storage refuses a `settledPaths` entry for a grouped arrow, so a group always restores by its shared offset. `simulateMove` supplies aggregate success/failure plus per-member `members` traces. The renderer uses equal travel distance for every member. `applyMove`, solver certificates and saved-state validation handle whole groups atomically. Reload must never restore partial group removal or failure history. Generated groups come from a seeded catalog in `overlapStarter` (`src/content/procedural.ts`, pairs on most ids and trios on ids divisible by three): classic, staggered, lanes, seam, wrap, fork, and seam-fork pairs, plus classic, trident, staggered, seam, and wrap trios. Members peel at different points and their individual bodies run straight or cross one or two cube seams through `stepSurface`, parking heads on faces away from the shared tail. Classic members turn their final legs outward, fork members turn theirs outward after a two-cell shared tail, seam-fork parks one head on the start face and the other past a seam, and trident is the fork pair plus a member running straight on, so heads leave on different faces or headings; `tests/group-divergence.test.ts` holds the share of groups over 16–200 with every head on one face and heading to at most 0.30 (0.265 measured). Attempts reject on head collisions, non-prefix cell sharing, route crossings, or exit-ray contacts before the caller's `validateLevel` gate, and member paths stay within the 40-cell generator bound. The group is placed first on every pass from level 16, and every member's track is reserved against the later spot placers that could land on it (the directional core, park-core spots, extra spots, and the flip core). Reversal blockers see only group bodies, but `reversalBlockers` validates each candidate spot and skips one the validator's group-through-spot rejection refuses, so a group track never costs a restart. A flip region may never hold a group member.

### Two-headed arrows

**Gameplay rules:** A double arrow is one logical arrow with violet and lime halves and an arrowhead at each endpoint. Selecting a half moves toward that half's head; a blocked choice collides normally even when the opposite endpoint is safe. A stop may park either moving head, and a parked double may resume in either direction. Directional spots bend the selected head. The first collision at one exact settled path costs one life and is shared by both endpoints; a new parked path has its own first failure. Failure preserves both colors and adds a whole-arrow red outline. Double arrows never join overlapping-tail groups, and hints highlight only the safe half.

**Introduction and generation:** Authored level 25 forces the violet tail move before its blocker can clear. `?feature=double` opens it without changing campaign saves. From level 26, `doubleArrowFrequency` rises from 0.20 to 0.45 by level 60; the independent `:double-plan` and `:double-core` streams optionally place one three-arrow required-use core, on the certificate tiers only. The generated double (`doubleCore`) is a 5–10 cell self-avoiding walk on one face that turns like a fill arrow. Blocker `b` occupies the two cells directly past its head and faces it, so the head end and `b` block each other, and blocker `a` aims from the side at a non-head body cell, so only the tail end can move first. Its endpoint-aware certificate contains a tail action, both endpoint routes validate, and placement exhaustion omits the optional core rather than rejecting the level. `tests/procedural.test.ts` requires at least half the generated doubles over 26–200 to bend and a median length of at least six (68 of 68 bend, measured).

**Implementation:** `MoveTarget` carries arrow identity plus endpoint through picking, safety checks, attempts, hints, tutorials, solver targets and animation. Single arrows and groups retain numeric `offsets` (except lone singles on flip levels, which store `settledPaths`); parked doubles store complete `settledPaths`, which are required because bends make a signed offset insufficient. Position failure keys use arrow id plus exact cell sequence. Renderer geometry splits by accumulated world-space length, gives both halves independent picker metadata and theme colors, and uses separate failure overlay meshes instead of replacing those colors.

### Flip spots

**Gameplay rules:** Every spot, static chevron or flip, has a current direction, and a head entering its cell takes that direction: travelling the spot's direction it passes straight through, travelling against it it reverses and runs back over its own body, and arriving from either side it bends onto it. A flip spot (`kind: "flip"`, drawn magenta as a dot plus one chevron) reverses its direction once the arrow has fully passed it, meaning no cell of that arrow remains on the spot. A head that re-enters a spot its own body still covers continues the same passage, so one passage flips once. An arrow that parks with part of its body on a flip spot leaves the flip pending until it later moves off. A collision rewinds the arrow and restores every spot to its direction at the start of the move, so a spot the arrow never cleared stays put and a pending flip stays pending. Another arrow entering an occupied spot cell is an ordinary collision; lives and red marks are unchanged.

**Introduction and generation:** Authored level 30 (`FLIP_INTRO_LEVEL`, seed `par-arrows:runtime:7:level:30:flip-intro:1`) teaches the bounce: the reverser U-turns out of the spot and flips it, the runner would now turn into the guard, so the guard clears first. `?feature=flip` (also `flips`, `flipspot`) opens it without changing campaign saves. From level 31 a `:flip-plan` stream draws a flip core with `flipCoreFrequency` rising linearly from 0.25 at level 31 to 0.65 at level 90 and holding; the `:flip-core` stream picks a `FLIP_PATTERNS` entry rotated about its first spot: gate and bounce (three arrows, one spot), relay (four arrows, one spot, two passes in a row), or relay2 (four arrows, two flip spots the traverser bends through in sequence). A level carries at most one flip core, so one to two flip spots. A planned core gets its own construction pass ahead of the ordinary passes in every tier; if the flip pass exhausts its restarts, the ordinary passes run on streams the flip pass never touches, so the level comes out exactly as it would with no flip plan. Flip spots are never required for solvability: they change which arrow is safe now, not whether the cube clears.

**Interaction regions:** Safety comes from proving the core's interaction region (`interactionRegion` / `proveRegion` in `src/core/validation.ts`). A region is the core's arrows closed under reachability: any arrow whose occupancy (body plus track from each end of a double, under every flip state) shares any cell with a region arrow's occupancy joins it, stop and spot cells included, up to six arrows (past that the region overflows and the placement fails). `proveRegion` enumerates the region's states with every outside arrow as a static blocker (a blocker only removes options, so the proof is conservative) and requires zero stranded states, `flipInterest` (some collision-free state has a tap whose safety depends on a spot's direction), and solvability. The order is: at placement, when the level has a circle to spare, `flipCore` proves the region with one circle planned on a core arrow's lane, trying first up to two cells where a park leaves a body on a flip spot (a pending flip, `parksOnFlipSpot`), then up to two cells where parking moves no core body onto another core arrow's track (`parkCrossesTrack`), then no circle, and the proven region's cells are reserved from later placement; after assembly, `flipRegionLead` re-derives the region on the finished level (later spots, circles and blockers can bend tracks toward it), rejects a region holding a shared-tail group member, proves it again, requires every outside arrow's reach under every flip state to stay off the region's cells, and solves the region on a board holding only its arrows and circles, which leads the certificate. If the assembled level fails, a cube with extra or reversal spots drops optional spots from the end of their placement order, choosing circles again and re-proving at each length down to the core-only set; otherwise the restart fails, and a flip pass that exhausts its restarts yields to the ordinary passes. In-region circles come out of the level's `getStopCount` budget. In practice every generated region equals its core.

**Implementation:** `GameState.spotHeadings` holds each flipped spot's current direction keyed by cell (absent means authored), read through `spotHeadingAt(level, cell, spotHeadings)`. `simulateMove` tracks the body on flip levels and reports `MoveResult.spotFlips` (`{ cell, step }`) for the renderer; `applyMove` writes `spotHeadings` only for `exit` and `paused`. On flip levels the loop key adds live spot state and body cells, and a repeated key returns `invalid` at no life cost; `loopError` in validation still walks each endpoint alone under authored headings. Validation rejects a flip spot on a stop circle and, on levels with stops, a stop that would park an arrow folded over itself: `foldedStopError` searches the arrow's own tap sequences (both ends of a double) from every flip-direction combination, carrying its own flips between legs, but does not model another arrow's flip between its legs. `solveKey` includes settled paths and spot state (entries equal to the authored heading dropped). The rule that no arrow outside a flip region reaches its cells is enforced by generation (`flipRegionLead`) and, for level 30, by its own enumeration test, not by `validateLevel`. The renderer turns a flip glyph (`palette.flip`) at its world-space share of travel (`flipTurnProgress`), snaps it at settle, and lifts later segments of a ribbon that folds over itself so the moving end draws on top. `render_game_to_text` reports each spot's `kind` and `current` direction, plus a `pendingFlips` list of flip spots a remaining arrow still covers.

### Wormholes

**Gameplay rules:** `LevelDefinition.wormholes` lists paired portal cells (`{ id, a, b }`), at most two per level (`MAX_WORMHOLES`). Travel is two-way: a head stepping onto an end is placed on the partner's cell in the same step, keeping its face-local heading — moving "up" in one face's grid leaves the partner moving "up" in the other's, whatever their 3D relationship — and the body follows cell by cell, so an arrow in transit occupies cells on both sides of the portal. A blocked exit is an ordinary collision: another arrow on the partner end or on the cell after it stops the head there, costs the usual first-failure life, turns the arrow or group red, and rewinds it back through the portal to its starting path; repeats are free. An arrow never collides with its own body, and a head re-entering a portal its own body still covers continues the same passage. A stop circle or spot may sit on the cell after an end, where an exiting head parks or bends normally; the ends themselves never share a cell with an arrow's starting cell, a stop, a spot, or another end. Two-headed arrows travel portals too, and a parked arrow may straddle one — its saved path carries the jump. A portal loop (a route that repeats a cell and heading) is rejected by validation and returns `invalid` at no life cost at runtime.

**Introduction and generation:** Authored level 35 (`WORMHOLE_INTRO_LEVEL`, seed `par-arrows:runtime:7:level:35:wormhole-intro:1`) teaches the deadlock the rings resolve: the portal arrow's lane ends on the gate's body at front(3, 2) and the gate's lane ends on the portal's head at front(1, 2), so both deadlock until the portal enters end A, leaves B heading east and flies off, vacating the gate's lane; a far-side blocker stands in the corridor cell east of B and leaves first, so the far end starts blocked like the near one. `tests/wormhole-content.test.ts` pins that the same cube with `wormholes: []` is unsolvable. `?feature=wormhole` (also `portal`, `wormholes`) opens it without changing campaign saves. From level 36 a `:wormhole-plan` stream draws zero to two wormholes with `wormholeFrequency` rising linearly from 0.25 at level 36 to 0.60 at level 90 and holding, and from level 50 a second draw on the same stream upgrades a hit to two with probability 0.3; plan zero draws nothing else, so every zero-wormhole level constructs exactly as before (see Generation and seeds). A planned hole gets a required-use core on the `:wormhole-core` stream: the level-35 three-arrow pattern (portal, gate and a far-side blocker) rotated about end A on a candidate face, with end B on a random other face whose exit corridor ahead runs straight off through a non-wrapping edge clear of every reserved cell, the blocker's body on the corridor's first cell and its own clear perpendicular exit, so the far end starts blocked like the near one. The core proves required use on the core board alone (solvable with the wormhole, deadlocked without it), every arrow already on board keeps its route off both ends so only the portal ever jumps, no earlier body sits on a core track so the core's certificate leads the replay, and the reservation stays off any shared-tail group's tracks. A planned hole whose core does not fit is dropped, so no wormhole placement ever restarts a level; there is no decorative fallback, because every wormhole must be functional and a pair on a dense board lands its ends on fill routes. Every later arrow's route keeps off the ends themselves, because entering one teleports: a starter whose straight lane runs over a reserved end redraws its lane, and sixteen straight misses withdraw the plan and rebuild the pass with zero slots, which is byte-identical to the plan-zero construction. Wormhole cells stay out of every flip region, so region proofs are unchanged.

**Implementation:** `src/core/wormholes.ts` holds the portal step: `advanceWithPortals` is the one head step `simulateMove` takes, so a jump is one step that carries `portal` (the entered end) on the forward info, and `linkHeading`/`pathHeading`/`isPortalLink` accept a portal jump wherever adjacency is expected. `simulateMove` reports each jump in `MoveResult.portals` (`{ from, to, step }`) for the renderer. On a wormhole level the loop checks in validation trace every route once per flip-spot state (`flipCombos`), because a portal can redirect a head into a spot-dependent route; without wormholes a single authored-state trace keeps the historical behavior, and the runtime repeated (cell, heading) state stays the no-life backstop. The renderer draws each end as a colored ring plus a partial-torus swirl (`createWormholes`), both ends of one wormhole sharing a color unique to it on the level (`palette.wormhole`, orange then deep blue; `userData.wormholeIndex` restyles both on a theme swap). Four direction dots sit on each end's perimeter, one per face-local side, in the four `palette.wormholeDots` colors (`userData.dotIndex` restyles them). `wormholeDotColorIndex(side, end)` turns end b's pattern half a revolution from end a's, so a head crossing a dot on either end leaves the partner across the dot of the same color, which shows the player the exit side in both directions. The ribbon splits at the portal: a portal link contributes zero world-space length as a gap with no bridge quad, and overlap lifting stays local to each side of the jump, so the head jumps from one end to the other as travel passes the gap. `render_game_to_text` reports each wormhole's `id`, both ends, and its `color` index.

### Rotor spots

**Gameplay rules:** A rotor spot (`kind: "rotor"`, drawn amber as one chevron inside a ring notched at each of the four headings) obeys the same entry rules as every other spot: a head travelling its direction passes through, one travelling against it reverses back over its own body, and one arriving from either side bends onto it. Where a flip reverses, a rotor turns its direction a quarter clockwise in face-local terms (north, east, south, west, north) once an arrow has fully passed it, so four passes bring it back to its authored heading. Passage, pending and collision rules are the flip's: one passage advances once, an arrow that parks with part of its body on the rotor leaves the advance pending until it moves off, and a collision restores every spot to its direction at the start of the move. A rotor may not share a cell with a stop circle, and a flip spot and a rotor may never share one interaction region (`mixedSpotRegionError` in validation).

**Introduction and generation:** Authored level 40 (`ROTOR_INTRO_LEVEL` in `rotor-intro.ts`, seed `par-arrows:runtime:7:level:40:rotor-intro:1`) is a 4 × 4 cube with one west-pointing rotor at front(2, 1). The turner runs east into it head-on, reverses out and exits, turning it north; the bender, which would have run straight on into the turner, then bends north through it and exits. The walkthrough gates the turner first. `tests/rotor-content.test.ts` pins that the cube with the rotor stripped is unsolvable; frozen at its authored heading it stays solvable but loses `flipInterest`, so the advance changes which tap is safe, not whether the cube clears. `?feature=rotor` (also `rotors`) opens it without changing campaign saves. From level 41 a `:rotor-plan` stream draws a rotor core with `rotorCoreFrequency` rising linearly from 0.25 at level 41 to 0.55 at level 90 and holding, drawn only when the level plans no flip core (a level is flip or rotor, never both) and has at least one circle in its `getStopCount` budget (`rotorCorePlanned`). The `:rotor-core` stream picks a `ROTOR_PATTERNS` entry rotated about its rotor: cycle-gate (three arrows) or lane-window (five arrows, whose play turns the rotor through all four headings). Each pattern's opener reverses off the rotor and parks on the pattern's own circle, which comes out of the circle budget, so the pass's parking core gets `getStopCount(id) - 1`. A pattern needs that circle because a rotor core that never parks can never require its rotor: a frozen rotor is a static spot, and a route an arrow has cleared only stays clear as the board loses arrows. The core board alone must be solvable, strand-free, and unsolvable with the rotor frozen at its authored heading. The rotor core fills the flip-core slot: it gets its own construction pass on the two certificate tiers only, and the region proof (`acceptFlipRegion`), reservations, fill-route bans and the certificate lead (`flipRegionLead`, whose seeds are `regionCoreIds`) all treat it as a flip core. A pass that exhausts its restarts yields to the ordinary passes, which share no stream with it, so a level that ends without a rotor core is the exact plan-zero construction. `tests/rotor-generation.test.ts` asserts one or two rotors on every rotor level; measured over 41–200, each of the 31 carries exactly one, because every pattern has a single rotor.

**Implementation:** Rotors share every flip mechanism. `GameState.spotHeadings` holds a turned rotor's current direction, `MoveResult.spotFlips` reports each advance, and `advancedSpotHeading` applies it (a flip reverses, a rotor turns clockwise through `rotatedHeading`). `spotStates(spot)` lists the directions a spot can hold (one for a static spot, two for a flip, four for a rotor), and validation's spot-state enumeration (`spotStateCombos`, `flipHeadingProbes`) multiplies those lists across stateful spots, so loop checks, `foldedStopError`, `occupancyKeys`, region closure and `proveRegion` cover all four rotor directions. `hasStatefulSpots` gates body tracking, and a lone single on a flip or rotor level parks by its exact cells in `settledPaths`, as parked doubles do. The renderer turns the rotor glyph (`palette.rotor`, restyled on a theme swap through `userData.spotKind`) by `spotTurnAngle("rotor")`, a negative quarter turn about the face normal, at its world-space share of travel (`flipTurnProgress`), and snaps it at settle to `spotStates(spot).indexOf(current)` advances. `render_game_to_text` reports each rotor's `kind` and `current` direction, lists a rotor a remaining arrow still covers in `pendingFlips`, and exposes `spotGlyphTurns`, the advances each flip or rotor glyph currently shows (fractional mid-turn).

### Fragile cells

**Gameplay rules:** `LevelDefinition.fragile` lists cracked cells, drawn as a jagged crack glyph. The first arrow whose route crosses one passes clean, and the cell collapses into a hole once that arrow has fully cleared it, meaning no cell of that arrow remains on it: the flip spot's passage timing. An arrow that parks with part of its body on the cell leaves the collapse pending until it moves off, and a collision rewinds the collapse along with the arrow. A head entering a collapsed cell does not collide: it turns inward along the face normal and falls into the cube, and the arrow, the whole shared-tail group, or the whole double is removed at the cost of one life. Every fall costs its life, and a red arrow that later falls pays again. There is no rewind and no soft-lock, because a fallen arrow is gone. Two routes may cross one cell: the first crosses clean and the second falls, so crossing order saves lives, never solvability. A fragile cell may not share a cell with an arrow's starting cell, a stop circle, a spot, or a wormhole end, and it may sit on any route. In a group, the earliest event decides the move; on one step a collision outranks a fall, which outranks a stop.

**Introduction and generation:** Authored level 45 (`FRAGILE_INTRO_LEVEL` in `fragile-intro.ts`, seed `par-arrows:runtime:7:level:45:fragile-intro:1`) is a 4 × 4 cube whose crosser and double share the bridge at front(1, 1): the crosser runs north over it, the double's head end runs west over it, and the double's tail end runs west into the crosser's body. The crosser must go first; the double then leaves by its tail. Sending the double's head across first leaves the crosser only the hole. The walkthrough gates the crosser, then the double's tail. A fragile cell only turns exits into falls, so any zero-fall solution replays on the same cube with the cell stripped to ground, and a stripped copy is never unsolvable. `tests/fragile-content.test.ts` pins the discriminator instead: the wrong order costs a life only with the crack present, and no order soft-locks the cube. `?feature=fragile` (also `fragiles`) opens it without changing campaign saves. From level 46 a `:fragile-plan` stream draws a fragile core with `fragileCoreFrequency` rising linearly from 0.25 at level 46 to 0.55 at level 90 and holding. The `:fragile-core` stream places `FRAGILE_PATTERN` (the level-45 crosser and a bent six-cell double) rotated about its cell. The core gets its own construction pass on the two certificate tiers, a copy of the tier's first pass with the core added after every other core, so earlier reservations and any flip or rotor region fence it. Every lane its arrows can travel (both ends of the double, under every spot state) and its cell must avoid every reserved cell, the park and group tracks, and every existing arrow's reach; no lane may enter the cell twice. On the core board alone the solver must find a zero-fall certificate that collapses the cell, the double-head-first order must end in a fall, and `hasSoftLockState` must find no soft-lock. The core's lanes are reserved, the cell is ray-forbidden to every fill route, and an assembled level where any arrow outside the core reaches the cell restarts. A plan whose core does not fit is dropped, and the ordinary passes share no stream with the fragile pass, so that id is the exact plan-zero construction. The core's certificate leads the replay. A level carries at most one fragile core. Measured over 46–200, 75 of 76 planned cores place (id 137 gives up); level 50 left the count when it became the authored lock cube.

**Implementation:** `src/core/fragile.ts` indexes fragile cells (`fragileKeys`, `hasFragileCells`) and derives `pendingCollapseKeys`. `GameState.collapsed` holds collapsed cell keys and `GameState.fallenIds` the removed fallen arrows. `simulateMove` tracks the body on fragile levels as on flip and rotor levels, reports `MoveResult.collapses` (`{ cell, step }`), and returns kind `fall` with `hole` when a head enters a collapsed cell; the body drains as it would past an exit edge, so a fall writes the collapses of every cell it clears. `applyMove` writes `collapsed` on `exit`, `paused` and `fall`, never on `blocked`. A collapse only ends a route, so the authored-state loop traces in validation already cover every collapse state and loop checks are unchanged. `solveKey` includes collapsed cells. The greedy clear refuses a drive that collapses a cell, because a hole can turn another arrow's exit into a fall, and `searchSolution` branches over collapsing exits the way it branches over parking; a fall is never a solution step, so certificates are zero-fall. `hasStrandingState` keeps its meaning (exits and pauses only), and `hasSoftLockState` counts a fall as progress. The renderer draws each fragile cell as a crack glyph (`palette.fragile`) and, once collapsed, a hole: a square floor sunk into the cube with four walls up to the face (`palette.hole.cavity`), masked by the stencil buffer to the opening, and a square border frame on the face (`palette.hole.rim`), all restyled on a theme swap through `userData.fragilePart`. A collapse opens the hole at its share of travel (`flipTurnProgress`) and snaps at settle. A fall's track runs to the hole's center, then turns inward along the face normal and sinks the whole body out of sight; the life-lost flash fires as the head reaches the hole. `render_game_to_text` reports `fragile` (each cell and whether it has collapsed), `pendingCollapses`, `fragileGlyphCollapse` (how far each hole currently shows), and `fallenIds`.

### Keys and gates

**Gameplay rules:** `LevelDefinition.locks` lists paired cells (`{ id, key, lock }`), at most two per level (`MAX_LOCKS`). While a lock is closed, a head entering its gate cell is terrain, not a collision: the attempt returns kind `gated` and the arrow or whole group rewinds at no cost, with no life lost, no red mark, and repeats free. A head crossing the key cell opens the paired gate for the rest of the level; keys are never consumed, a re-cross is idempotent, and the key cell is ordinary floor. A head that crosses a key and then the same lock's gate in one move passes through. An unlock is written like a fragile collapse: on `exit`, `paused` and `fall`, never on `blocked` or `gated`, so a failed move rewinds its unlocks with the arrow. An open gate is ordinary floor, so a second arrow meeting an arrow parked over it collides normally. Gate and key cells may not share a cell with an arrow's starting cell, a stop circle, a spot, a wormhole end, a fragile cell, or another lock cell. In a group, the earliest event decides the move and on one step a collision outranks a gate, which outranks a fall, which outranks a stop; members read the move-start lock state, so one member crossing a key opens its gate only for later moves.

**Introduction and generation:** Authored level 50 (`LOCK_INTRO_LEVEL` in `lock-intro.ts`, seed `par-arrows:runtime:7:level:50:lock-intro:1`) is a 4 × 4 five-life cube whose opener sits at the left of front row 1 with a short lane east barred by the gate at front(2, 1). The key arrow is the long bent one: its lane runs north up column 3 over the key at front(3, 0), crossing the opener's lane past the gate. The walkthrough gates the key arrow first, then the opener. `tests/lock-content.test.ts` pins the discriminator: with `locks: []` the opener can leave first and the solver takes it first. `?feature=lock` (also `locks`, `keylock`) opens it without changing campaign saves. From level 51 a `:lock-plan` stream draws a lock core with `lockCoreFrequency` rising linearly from 0.25 at level 51 to 0.55 at level 90 and holding. The `:lock-core` stream places `LOCK_PATTERN` (opener, bent key arrow and key cell) rotated about its gate. The core gets its own construction pass on the two certificate tiers, a copy of whatever pass would otherwise run first, placed after every other core, so earlier reservations and any flip or rotor region fence it. The key arrow's lane must cross the key and never the gate, the opener's lane must reach the gate and never the key, and every lane, the gate and the key must avoid every reserved cell, the park and group tracks, and every existing arrow's reach. On the core board alone the opener's first tap must be `gated`, the stripped core must let the opener exit, the solver's certificate must send the key arrow before the opener, and neither `hasStrandingState` nor `hasSoftLockState` may find a bad state. The core's lanes are reserved, the gate and key are ray-forbidden to every fill route, and an assembled level where any arrow outside the core reaches either restarts. A plan whose core does not fit is dropped, and the ordinary passes share no stream with the lock pass, so that id is the exact plan-zero construction. The core's certificate leads the replay right after the fragile core's. Measured over 51–200, 78 of 79 planned cores place. The lock pass copies the first pass, so on a fragile-planned id it carries the fragile core too; id 137's fragile core never fits, so its lock pass gives up before the lock is tried.

**Implementation:** `src/core/locks.ts` indexes gates and keys (`gateAt`, `keyAt`, `hasLocks`) and derives `closedGateKeys`. `GameState.unlocked` holds opened lock ids. `simulateMove` checks the gate before a hole on each step, returns kind `gated` with `gate` when a head meets a closed one, and reports `MoveResult.unlocks` (`{ id, cell, step }`, `cell` being the gate) as the head crosses keys. `applyMove` returns a `gated` result as a new state with only the revision advanced, so the rewind is an accepted, animated outcome that costs nothing. `solveKey` and the fold search carry the unlocked set, and `replayCertificate` in `procedural.ts` records unlocks between entries. The solver never takes a `gated` tap, so certificates never pass through a closed gate. The renderer draws each gate as a square frame with three vertical bars and each key as a ring bow with a toothed blade, both in the lock's color (`palette.lock`, green then deep blue, restyled on a theme swap through `userData.lockIndex`). A gate opening mid-move lifts its bars and fades its frame at its share of travel (`flipTurnProgress`) and snaps at settle; a `gated` attempt animates out and back like a rebound with no life flash. `render_game_to_text` reports each lock's `id`, `key` and `lock` cells, `open` state and `color`, plus `unlockedIds` and `lockGlyphOpen` (how far each gate currently shows open).

### Mirror cells

**Gameplay rules:** `LevelDefinition.mirrors` lists reflecting cells (`{ cell, orientation: "/" | "\" }`), at most two per level (`MAX_MIRRORS`). A head entering a mirror cell leaves along the heading reflected across the cell's diagonal: a "/" maps east to north, north to east, west to south and south to west, and a "\" maps east to south and north to west. Unlike a spot the result depends on the entry heading, so the same mirror routes two approaches to two destinations; reflection is an involution, so a head re-travelling its outgoing heading retraces the entry line reversed. A mirror is static floor with no state: no `GameState` field, no pending timing, and a collision after the bend rewinds exactly like any other collision. A mirror may not share a cell with an arrow's starting cell, a stop circle, a spot, a wormhole end, a fragile cell, or a lock cell, and a shared-tail group may not route through one (the same shared-offset soundness rule as spots).

**Introduction and generation:** Authored level 55 (`MIRROR_INTRO_LEVEL` in `mirror-intro.ts`, seed `par-arrows:runtime:7:level:55:mirror-intro:1`) is a 4 x 4 five-life cube whose silver "/" sits at front(1, 1) between a face-off pair: the north arrow's straight lane ends on the south arrow's head and the south arrow's straight lane (arriving over the top seam) ends on the north arrow's head, so the stripped cube is deadlocked and either order clears once the mirror bends each approach down its own corridor. The walkthrough gates the north arrow first. `tests/mirror-content.test.ts` pins the discriminator: the same cube with `mirrors: []` is unsolvable. `?feature=mirror` (also `mirrors`) opens it without changing campaign saves. From level 56 a `:mirror-plan` stream draws a mirror core with `mirrorCoreFrequency` rising linearly from 0.25 at level 56 to 0.55 at level 90 and holding. The `:mirror-core` stream places `MIRROR_PATTERN` (the two face-off arrows) rotated about its mirror. The core gets its own construction pass on the two certificate tiers, a copy of the pass ahead of it (so on a lock-planned id it carries the lock and fragile cores too); a pass that exhausts its restarts yields to the pass below, so that id is the exact plan-zero construction. The reservation traces each face-off arrow's POST-mechanic route on a board that carries the mirror, because a mirror bends its arrows off their straight tracks — unlike the lock and fragile cores, whose exit lanes stay on their pre-mechanic lanes. Every lane and the mirror cell must avoid every reserved cell, the park and group tracks, and every already-placed core's body (already-placed cores move only after the mirror certificate replays, so their tracks crossing a corridor are harmless). On the core board alone the solver must clear it, the stripped board must be deadlocked, and neither `hasStrandingState` nor `hasSoftLockState` may find a bad state. The core's lanes are reserved, the mirror cell is ray-forbidden to every fill route, and an assembled level where any arrow outside the core reaches the mirror cell restarts. Measured over 56-200, 73 of 83 planned cores place.

**Implementation:** `src/core/mirrors.ts` indexes mirrors (`mirrorAt`, `hasMirrors`) and derives `reflectedHeading`/`mirrorHeadingAt`. Every movement walk applies the reflection after spot state and before the plain heading: `simulateMove` at runtime, `arrowTrack` for parked-window and occupancy derivation, and validation's `loopError` and `selfPassageError` traces. Perpendicular reflection means a lone mirror can never fold a straight body back over its own arrow, and mirrors never sanction a self-passage (only a head-on spot reversal does), so the fold rule needs no mirror branch. The solver and `foldedStopError` drive `simulateMove` and inherit mirrors unchanged; `solveKey` is untouched because mirrors hold no state. The renderer draws each mirror as a silver diagonal slash (`palette.mirror`, restyled on a theme swap through `userData.mirror`) rotated by `mirrorSlashAngle` along its diagonal. `render_game_to_text` reports each mirror's `cell` and `orientation`.

### Leap pads

**Gameplay rules:** `LevelDefinition.leaps` lists leap pads, at most two per level (`MAX_LEAP_PADS`). A head entering a pad skips the next cell in its heading and lands two cells on; the skipped cell is never entered, so nothing on it triggers — no collision, no gate, key, hole, stop, spot, mirror, or portal. Only entered cells trigger. Both hops are ordinary topology steps, so a wrapping edge wraps whichever hop crosses it; when the landing is off the cube the head exits past the skipped cell, and when even the first hop is off it the head exits at the pad's edge like an ordinary step. A portal on the landing cell still fires: the landing is an entered cell. A pad is static floor with no state: no GameState field, and a collision after the bend rewinds exactly like any other collision. A pad may not share a cell with an arrow's starting cell, a stop circle, a spot, a wormhole end, a fragile cell, a lock cell, or a mirror, and a shared-tail group may not route through one (the same shared-offset soundness rule as spots).

**Introduction and generation:** Authored level 60 (`LEAP_INTRO_LEVEL` in `leap-intro.ts`, seed `par-arrows:runtime:7:level:60:leap-intro:1`) is a 4 x 4 five-life cube whose pad sits at front(1, 1) in front of a closed gate: the leaper's lane crosses the top seam into front(1, 0) and heads south over the pad, leaping the barred cell (1, 2) and landing on the gate's key at (1, 3) before exiting, which opens the gate for the barred arrow's east lane. The walkthrough gates the leaper first, then the barred arrow. `tests/leap-content.test.ts` pins the discriminator: the same cube with `leaps: []` is unsolvable, because the gate is terrain nobody can pass and the key behind it is unreachable. `?feature=leap` (also `leaps`, `leappad`) opens it without changing campaign saves. From level 61 a `:leap-plan` stream draws a leap core with `leapCoreFrequency` rising linearly from 0.25 at level 61 to 0.55 at level 90 and holding. The `:leap-core` stream places `LEAP_PATTERN` (the leaper and a bent blocker) rotated about its pad: the blocker's body covers the pad's skip cell and its head points back at the leaper's head, so each lane ends on the other's body and the pad alone breaks the deadlock — the leaper leaps over the blocker's body and exits past it, and the blocker then leaps the same pad in the other direction over the vacated cells. The core gets its own construction pass on the two certificate tiers, a copy of the pass ahead of it; a pass that exhausts its restarts yields to the pass below, so that id is the exact plan-zero construction. Only the leaper's lane crosses the pad (the blocker's lane is the plain run it drives once the leaper has vacated its head cell), the reservation traces both lanes on the pad-carrying board, every lane and the pad must avoid every reserved cell, the park and group tracks, and every already-placed core's body, and an assembled level where any arrow outside the core reaches the pad restarts. On the core board alone the solver must clear it, the stripped board must be deadlocked, and neither `hasStrandingState` nor `hasSoftLockState` may find a bad state, with the leaper leaving before the blocker. The core's lanes are reserved, the pad is ray-forbidden to every fill route, and the core's certificate leads right after the mirror's. Measured over 61-200, 74 of 81 planned cores place.

**Implementation:** `src/core/leaps.ts` indexes pads (`isLeapPad`, `padKeys`, `hasLeapPads`) and derives the leap step (`leapForward`, the pad-aware sibling of `advanceWithPortals`) and leap links (`leapLinkHeading`). The movement loop, `arrowTrack`, and validation's loop and self-passage traces pick `leapForward` whenever the head sits on a pad, so a leap costs one step of the walk but two cells of travel (`distance` counts 2) and the skipped cell is never in the route. `MoveResult.leaps` reports each hop (`{ from, over, to, step }`) for the renderer; a leap landing on a portal end reports the physical landing in `to` and the jump in `portals`. `linkHeading` resolves a pad's links only through the leap, so storage accepts parked paths whose consecutive links include a leap. Pads are stateless, so `solveKey` is untouched and no spot-state enumeration is needed. The renderer draws each pad as an amber half-torus arch over its cell (`palette.leap`, restyled on a theme swap through `userData.leap`), a leap link contributes a gap with no bridge quad so the head jumps it like a portal, and `render_game_to_text` reports `leaps` as the list of pad cells.

### Pointer targets

`src/pick.ts` holds `resolvePick`, the pure rule that turns the renderer's ranked
candidates into one arrow. `PuzzleRenderer.pickCandidates` reports every arrow a
press could mean: a ray hit scores a zero gap, and any other arrow within the
margin scores the screen distance to its exposed ribbon or head. The margin is a
fingertip in CSS pixels (`TOUCH_PICK_MARGIN_PX` for touch, `MOUSE_PICK_MARGIN_PX`
otherwise), never scaled by grid density. Arrows the press landed on outright
exclude ones it merely came near, so a press aimed squarely at an arrow always
keeps that arrow; among whatever is left, an arrow whose move avoids a collision
beats a nearer one that would cost a life, and the closest arrow settles the
rest. The renderer ranks but never decides — move legality stays in `app.ts`,
which supplies the safe test that `beginHint` also uses. `tests/pick-browser.ts`
pins the widened zone against a measured baseline and proves the preference
by the life count rather than by projected centroids.

### Generation and seeds

Levels 1, 5, 11, 15, 20, 25, 30, 35, 40, 45, 50, 55, and 60 are authored and keep their own seeds: level 1 uses `par-arrows:runtime:1:level:1`, level 5 `:stop-intro:1`, level 11 `:wrap-intro:1`, level 15 `:overlap-intro:1`, level 20 `:directional-intro:1`, and levels 25, 30, 35, 40, 45, 50, 55 and 60 the v7 `:double-intro:1`, `:flip-intro:1`, `:wormhole-intro:1`, `:rotor-intro:1`, `:fragile-intro:1`, `:lock-intro:1`, `:mirror-intro:1` and `:leap-intro:1` seeds. Every generated id uses the generator v10 seed `par-arrows:runtime:10:level:<id>` (`GENERATOR_VERSION`, `seedForLevel`, `MAX_LEVEL_ID`). `tests/fixtures/v8-layouts.json` pins the `layoutFingerprint` of every level 2–200 (the path name is kept across releases; it carries the v10 fingerprints, and `scripts/write-layout-fixture.ts` regenerates it), and `tests/flip-generation.test.ts` checks every one of them against it; `tests/wormhole-generation.test.ts` sweeps ids 36–200 for wormhole caps, validation, and flip-region disjointness. Rotor cores changed the fingerprints of exactly the generated ids that place one (44, 58, 64, 68, 88, 91, 94, 95, 96, 109, 116, 121, 124, 133, 134, 136, 142, 143, 150, 161, 165, 166, 171, 172, 173, 178, 184, 187, 189, 197; 137's rotor pass has given up since the self-passage placement rule) and no other; `tests/rotor-generation.test.ts` keeps their pre-rotor fingerprints and requires every other id to match the fixture. Authoring level 45 changed its fixture entry, and fragile cores changed exactly the 76 generated ids that place one; `tests/fragile-generation.test.ts` keeps their pre-fragile fingerprints the same way. Authoring level 50 changed only its own fixture entry, because a generated seed embeds its id rather than a position in a sequence, and lock cores changed exactly the 78 generated ids that place one; `tests/lock-generation.test.ts` keeps their pre-lock fingerprints.

**Construction.** `generateLevel` places the cores first: the shared-tail group from level 16, the parking core, the directional core, the double core, the wormhole cores, the flip or rotor core, the fragile core, the lock core, the mirror core, then the straight and wrap starters. `dependencyFill` (`src/content/dependency-fill.ts`) then fills the cube. The group and the starters enter it as existing graph nodes, and every other lead arrow stays outside the graph. A fill arrow's route may run through other arrows' bodies; each body on the route becomes a "must leave first" edge, and a candidate that would close a cycle is rejected, so the graph stays acyclic and a topological order clears it. With probability `clearShare(id)` a placement must have a clear route instead: 1.0 on levels 2–4, then 0.95 at level 6 falling linearly to 0 at level 60 and holding. The dial applies at placement time only, so later placements and tail growth can still cover an earlier clear route. A fill head never sits on its exit edge, because its route must hold at least one cell. After placement, fill tails grow into leftover empty cells, up to the 40-cell path bound, without creating a cycle. `level.arrows` is emitted with the graph nodes in reverse removal order followed by the lead arrows, and the certificate is the flip or rotor region lead, the fragile core, the lock core, the mirror core, the wormhole cores, the double core, the park legs, the park-core arrows in reverse placement order, the directional core, then the reversed graph section.

**Reservations.** Every lead arrow's track (both ends of a double, and every spot state for the flip or rotor core) is forbidden to fill bodies, as are the park-core tracks. Fill routes come from `routeFrom`, which sees only wrap edges, so no fill route may cross a circle, a spot placed before the fill, a flip-region cell, a portal end, a fragile cell, a lock's gate or key, or a park track: a spot would bend the route, an end would move it, a second crossing would fall, a closed gate would stop it, a key would open a gate outside the lock core's proof, and a crossing park track strands the core circle. Double, directional-corridor and wormhole-core tracks are crossable, because those leads have left before any fill arrow moves.

**Arrow counts.** Fill is exact to `getLevelConfig`'s `arrowCount`. Through level 42 it is `max(36 + 2·id, round(0.075 · 6 · grid²))` (45 at level 2, 146 at level 42), levels 43–57 use `150 + 2·(id − 43)`, and after 57 the count rises 2 per level to its 200 cap at level 68. `MAX_GENERATED_ARROWS` is 200, the largest fill target; nothing adds arrows past it, and `tests/procedural.test.ts` asserts the ceiling. Grids grow from 10 to 18 (`min(18, 10 + floor(id / 4))`). Certificate tiers restart a board whose bodies cover less than 0.78 of a cube of grid 13 or larger (`skip = "coverage"`), and the final tier accepts it.

**Tiers.** `generateLevel` tries three acceptance tiers in order: two certificate-replayed tiers, then a final tier that trades the certificate for a solver-proven level instead of throwing. Tier 0 keeps the unsalted construction seeds, and each later tier salts the restart RNG by its tier index so it never replays a rejected earlier tier. Measured over 2–200, the slowest id takes about 0.5 s (about 1.3 s on CI since the mirror pass, about 3.4 s since the leap pass); the mechanic-sweep budget pins (depth, rotor, fragile at four seconds per sampled id since the wormhole far-side blocker, lock at four since the leap pass).

Stop-circle counts come from `getStopCount` on a stream independent of layout retries. Levels with at least one circle gain a parking-required deadlock core placed on its own `:park-core` stream, which also seeds the pattern choice from the catalog (multi-circle patterns need a stop budget that covers them); core placement failure falls back to decorative circles rather than restarting construction, and any remaining circles stay decorative on cells some arrow's head actually travels through. No collision-free move may make a level unwinnable: a decorative circle is accepted only when every arrow that can park on it moves onto no cell another arrow's track uses (`strandSafeCircle`), a level places fewer circles when too few cells pass, and each parking core must enumerate with zero stranded states (`hasStrandingState`). Circles inside a flip region are proven by the region's own enumeration instead (see Flip spots), so a region park may cover a flip spot and leave its flip pending; that enumeration, not the frees-cells rule, keeps it strand-free. A rotor core's circle is proven the same way, and it is taken from the circle budget before the parking core draws (see Rotor spots). Generation is deterministic from the seed, retries preserve selected wrapping seams (separate seeded stream), and generated layouts are validated by the solver. Wrapping-edge counts follow a level-scaled distribution (`getWrappingEdgeWeights`). From level 21, every cube draws zero to four static-spot-bearing faces (`directionalFaceCount` on a `:dir-plan` stream) with one to four static spots per bearing face (`directionalFacePlan` on `:dir-counts`, faces from `:dir-faces`); these caps cover static spots only, because a flip core's one or two spots (always on one face) or a rotor core's one rotor are added on top (see Flip spots and Rotor spots), so a face can carry up to six spots and a cube a fifth spot-bearing face. A cube with any static spots embeds the required head-on core from a `:dir-core` stream — the spot cell and its whole bent exit corridor are reserved from later placement (a later route may cross the corridor, since the core replays first, but no later body may sit on it), the core stays clear of any shared-tail group's tracks (see Overlapping tails), and the level must be unsolvable with the static spots removed. From level 21 one traverser may bend through two spots and from level 40 through three (`chainDepthLimit`); extra spots are placed on travelled cells by `extraDirectionalSpots`, which prefers candidates whose traverser already bent through an earlier placed spot so chains emerge from chain-first candidate ordering before plain single-bend candidates fill in, with a post-trial recheck rejecting a candidate that would push any traverser past the limit (a new spot can redirect a traverser onto a corridor with more bends than its pre-redirect track showed, so the pre-trial depth tag alone cannot be trusted); each candidate tries its seeded perpendicular turn and then the other one, and is further vetted so every traverser still exits alone with its bent route clear of earlier-replaying arrows, the parking core's tracks and the flip region, and if the extras break the certificate replay, the cube drops optional spots from the end of their placement order (extras, then reversal spots) until the rest replays, down to core-only, with a cube whose directional pass exhausts its restarts rebuilding with the plan forced empty (spots are optional at zero faces). After the extra spots, `reversalBlockers` spends up to one or two (seeded) of the spots left in each planned face's count on head-on static spots that bounce a plain arrow back over its own body into a lane exactly one other arrow's track uses; each is kept only if every arrow crossing the cell still exits alone within `chainDepthLimit` and stays off earlier-replaying arrows, the parking core's tracks and the flip region, and the same trimming drops them first. A trimmed board re-measures closure against the depth gate; its arrows are unchanged, so its coverage is too. Optional required-use double cores come from level 26 on independent `:double-plan` / `:double-core` streams. Rotor cores come from level 41 on independent `:rotor-plan` / `:rotor-core` streams, only on levels with no flip plan and at least one circle (see Rotor spots); like the double core, the rotor pass runs only on the two certificate tiers. Optional required-use wormhole cores come from level 36 on independent `:wormhole-plan` / `:wormhole-core` streams — at most two wormholes, the second only from level 50 (see Wormholes for the full placement and give-up rules); like the double core, the slots exist only on the two certificate tiers, and a give-up below withdraws them so the pass rebuilds as the exact plan-zero construction. `tests/mechanic-counts.test.ts` holds each mechanic's placement ratio over 2–200 (static spots, wormholes, flip cores, doubles) within 10% of its v9 value — wormholes at 0.8x since the far-side blocker started shipping with every core — and rotor cores within 10% of the 31 placed of 31 planned measured when they shipped, fragile cores within 10% of the 76 placed of 77 planned measured when they shipped, and lock cores within 10% of the 76 placed of 79 planned measured after the far-side blocker cost ids 133 and 144 their cores, and requires every planned circle and every group from level 16 to be placed. The fill rejects a candidate, and tail growth rejects a grown path, whose `canonicalShape` (run lengths and relative turns of a single-face path of four or more cells, canonical under rotation, mirroring and reversal) already has `shapeCap(arrowCount)` copies on the level, so no short zigzag gets stamped across a cube; `tests/shape-variety.test.ts` enforces the cap over ids 12–200. A head one step past a cube seam continues along the heading it entered its face with (`headingForPath` maps the final link through `seamTransition`). Any change to a level's layout or seed string refreshes saved attempts on it once (see Storage); because every generated seed embeds `GENERATOR_VERSION`, bumping it refreshes every generated level's saves, while the authored seeds do not change.

### Depth gate

Every generated level must meet a closure gate (`meetsDepthGate` in `src/content/difficulty.ts`). `closureStats(level)` runs on the fully assembled board with wormholes stripped. A tap unit is a single arrow or a whole shared-tail group (`overlappingArrowIds`), whose members' routes union. A unit's prerequisites are every other unit with a body anywhere on its route past its own body, and its closure is the number of units reachable through those prerequisites. A double counts as one unit whose two routes are kept apart, and its closure is the smaller of the two. `closureStats` returns `median` (the median closure over units), `deepShare` (the share of units with closure at least `DEEP_CLOSURE`, 15) and `freeShare` (the share with closure 0). The curves are piecewise-linear through waypoints and hold flat past the last one:

- `medianTarget` is 0 through level 11, then 2 at 12–20, 6 at 40, and 12 from 60, rounded to a whole number.
- `deepShareTarget` is 0 through level 12, then 0.06 at 20, 0.36 at 40, and 0.48 from 60.
- `freeCap` is 0.40 through level 10, then 0.26 at 20, 0.21 at 40, and 0.16 from 60.

`GATE_TOLERANCE` is 0.1 and relative: a board passes at 0.9 of each floor and 1.1 of the cap. The targets are floors set at or below each band's measured 10th percentile (the cap at or above its 90th), not typical values; a typical late board measures a median closure of about 31. `clearShare(id)` is the dial that sets depth. Both certificate tiers restart a board that misses the gate (`skip = "depth"`), including a board trimmed of optional spots; the final tier accepts a short board rather than throwing. `tests/depth-generation.test.ts` sweeps ids 2–200 and requires every one to meet the gate and to reach coverage of at least 0.78 on every grid of 13 or larger and a nonempty route for every fill arrow, checks that no fill route enters a wormhole end, bounds generation under one second on sampled ids, and pins determinism. `scripts/measure-boards.ts` prints each id's arrow count, coverage, closure stats and generation time.

### Storage

`localStorage` under `par-arrows:campaign:v1` / `par-arrows:settings:v1` keys with `CONTENT_VERSION = 18` guarding the logical save. Every save writes `layout`, the resolved level's `layoutFingerprint` (the first 16 hex characters of the SHA-1 of `JSON.stringify(level)`), plus the generator version and seed. An attempt resumes only when the save is content 18, its `layout` equals the resolved level's fingerprint, and its seed equals `seedForLevel` for that level; the stored generator version is not compared. Every other save, including any older content version, refreshes the attempt once while preserving level, unlocks, and tutorial completion. There is no per-version migration table. Group removal and failure history must be all-or-none, and lives count failed groups once. Saved `offsets` are validated against each single arrow's track length, group members must share one offset, a grouped arrow may never carry a `settledPaths` entry (so a forged single-member group park is rejected), and no two arrows may be parked onto the same cell. Parked double `settledPaths` must have the authored length, valid unique cells whose consecutive links are adjacencies or wormhole portal jumps, name a remaining double arrow, and be reachable through legal pauses; on flip and rotor levels a parked single's `settledPaths` entry is checked structurally and must end on a stop circle, and saved `spotHeadings` may name only flip and rotor spots, each holding one of its `spotStates` (a flip its own axis, a rotor any of its four directions); `failedPositions` must match the authored or current settled path. Saved `collapsed` cells must be distinct authored fragile cells that no remaining arrow sits on, and `fallenIds` must name removed arrows, whole groups at a time, on a level with fragile cells; each fall counts one life in the lives check, and a fall that spends the last life saves as `lost` even when it empties the board. Saved `unlocked` ids must be distinct authored lock ids, and no remaining arrow may rest on a gate that is still closed; an unlock never costs a life, so it takes no part in the lives check. The browser test hooks (`window.render_game_to_text` etc.) are enabled only by `?test=1`; `?test=1` alone does not start preview mode. The diagnostic exposes `mode` as `campaign` or `preview` — any `?level`/`?feature` session is a preview and never writes campaign saves.
